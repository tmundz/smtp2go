## What I Found

### LOGIN_AS accepts any integer — no rejection
`POST /api/login/?CSRF_key=<X>` with `{"LOGIN_AS": <any_int>, "STACK": "STACK"}` always returns:
```json
{"status": "OK", "message": "Log in Successful", "login_id": "<token>"}
```
Even `LOGIN_AS=0` and `LOGIN_AS=999999999`. The server does not validate whether the ID exists
before returning "Log in Successful". This is unexpected behavior — a non-existent subaccount
should return an error.

### Soft fallback — tokens authenticate as master account
When stolen tokens are used to call `/api/settings/team/`, all return Account A's data
(roy kent / 0xcaphe+roy). This means the server silently falls back to the master account
when the target subaccount doesn't exist under the caller.

### Accounts have no subaccounts — blocks definitive IDOR test
Both Account A (1010395) and Account B (1015003) have `subaccounts: []`. Without a valid
`record_id` from Account B's real subaccount, we cannot confirm whether the server:
a) Properly scopes LOGIN_AS to the caller's own subaccounts (auth OK)
b) Accepts any valid subaccount ID regardless of owner (IDOR)

The "soft fallback" behavior suggests (b) is likely — if the server truly scoped it, it
would return an error for non-owned IDs rather than silently falling back.

## Current Hypothesis

The most likely scenario: the server's LOGIN_AS handler does:
1. Receives record_id
2. Looks up subaccount by record_id in DB
3. If found AND owned by caller's master: log in as that subaccount
4. If NOT found (or not owned): silently fall back to master account login (the bug we see)
5. Never explicitly checks ownership — just falls back

If step 4 is "if found, log in regardless of ownership" (no ownership check), then it's full IDOR.
The soft fallback behavior is consistent with a missing ownership check combined with a missing
"not found" error path.
