## CRITICAL: SSTI IS DEAD — NOT Jinja2

The template engine is **Handlebars (pybars)**, NOT Jinja2.

### Evidence
```
Template body: RESULT:{{7*7}}:END
render-text response:
"An error occurred rendering the template for, error: Parse error on line 1:
Lexer error
Token: Error{\"Unexpected character in expression: '*'\"}"
```

`{{7*7}}` fails at the Lexer stage because `*` is not a valid Handlebars identifier character. Jinja2 would evaluate this as `49`. This is definitive — it's Handlebars.

### Context scope confirmed
`{{#each this}}KEY:{{@key}}=VAL:{{this}}{{/each}}` with `template_variables={"first_name":"Alice","email":"test@test.com"}`
→ `KEY:first_name=VAL:AliceKEY:email=VAL:test@test.com`

The context is ONLY the `template_variables` dict. No Flask config, no request object, no internal state exposed. Classic Handlebars sandbox.

### Implication
- SSTI for RCE: ❌ DEAD — template engine is logic-less Handlebars
- Template injection for HTML injection/stored XSS: still possible via template_variables values containing HTML (if not escaped)
- The `{{ first_name }}` syntax in smtp2go docs misled us — it's Handlebars, not Jinja2

**Interpretation**: The `action=registrar` endpoint does a WHOIS/registrar lookup on domain NAMES, not HTTP fetches to IPs. IP addresses return "Unknown" because they don't have a registrar record. This is NOT a full-read HTTP SSRF. It's DNS/WHOIS-based only.

**Can't escalate to internal service access via registrar.** The vector is essentially blind SSRF at best (server contacts WHOIS service, not internal HTTP endpoint).
