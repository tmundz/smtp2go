## Key Technical Findings

### The `status_code === -1` diagnostic
When the server can't complete the fetch, `el.status` contains the raw Python/requests
exception message. This is shown in the test results UI as the response text.
The exception message directly tells you WHY the request failed:
- "Connection refused" → server tried, port closed (SSRF alive)
- "timed out" → network block or service not responding
- "Invalid URL" → Python requests rejected the scheme/format
- "host not allowed" → application-layer blocklist
- "Name or service not known" → DNS failure (domain doesn't resolve)

This makes the webhook test surface much more informative than typical blind SSRF.

### Client-side validation: empty string only
From webhooks.tag:
```js
if (fd.url.length == 0) { show error }
else { clear error }
```
No scheme check. No IP regex. No private range check. Zero.
Whatever validation exists is entirely server-side.

### IP Allowlist ≠ URL allowlist
The `/api/settings/ipallowlist/` endpoint (present on every page) is for
*login IP allowlisting* — restricting which IP addresses can log into the account.
It has nothing to do with webhook URL validation. Do not confuse the two.

## Bypass Techniques — Priority Order for This Target

1. **Decimal IP** (`http://2130706433/`) — Python's `ipaddress` module and `urllib` both
   accept integer IPs. Many blocklists only check string patterns like "127." or "localhost".

2. **DNS rebinding** (`localtest.me` resolves to 127.0.0.1 in many configs) — works if
   blocklist does IP check at validation time but fetch happens later.

3. **Redirect chain** (your server 301 → internal) — works if server follows redirects
   after validation. Python `requests` follows up to 30 redirects by default.

4. **IPv6 localhost** (`http://[::1]/`) — often missed by blocklists checking for "127.0.0.1"

5. **`@` URL confusion** (`http://evil.com@127.0.0.1/`) — some parsers use the pre-@ part
   as the hostname, others use post-@. Python requests uses post-@.

## Alternative Surfaces Priority

1. `fileurl` in email API — completely different code path, different Python service
2. Domain verification redirect chain — if HTTP verify fetches your URL
3. WebhookProcs retry — fires stored URL again (if saved bad URL gets retried)
4. CSPT-003 stream_url — unknown if server-side fetch involved
