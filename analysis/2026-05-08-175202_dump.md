## What I Found
1. **verify_auth generates NEW TOTP secret on every call** — these are proposed secrets, not the active login secret. Proven by calling 3x in a row and getting different secrets each time.

2. **verify_app_2fa (enable mode, auth_to_disable="") validates against CLIENT-SENT totp_secret_key** — not stored active secret. Confirmed by enabling TOTP for Ted with attacker-generated key pair. Ted's login then required the attacker's TOTP. MFA-008 documented.

3. **Accounts WITH TOTP correctly reject re-enable** — "Authentication already exists. Disable existing authentication to setup another authentication." So can't replace existing TOTP via this path.

4. **use_auth=email downgrade confirmed AGAIN** — multiple fresh sessions, all show `sms-verification-message`, "Enter the verification code sent to", `resend-sms`. Still blocked by inbox access.

5. **Roy's actual TOTP secret was different from what I had** — LOAOHN3C2OYNP36QQPI4ZM6OSUQYZLX5 was old/from setup; actual current active secret changed. This explains why my earlier TOTP attempts failed.

6. **CSRF_key IS validated** — wrong key returns "login-required", empty key returns 500. Protection works on 2FA settings API. The /login/2fa/ and /forgot-password/ endpoints still lack CSRF protection.
