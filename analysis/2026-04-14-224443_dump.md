### WCD FINDINGS

**Critical observation**: ALL 20 frontend HTML pages (dashboard, reports, settings, account)
return status 200 with `Cache-Control: MISSING` — they have NO cache directive whatsoever.

These pages embed:
- `HTML.csrfkey = '<token>'` — hardcoded into every page
- `apMetadata` JSON blob (on 7 pages) — contains `sponsor: 1010395`, SMS limits, plan flags
- Sponsor ID `1010395` inline in `/settings/subaccounts/` HTML
- Chargebee.js billing integration on `/account/updatebilling/` and `/account/changeplan/`

If any caching intermediary (CDN later added, reverse proxy, Cloudflare Trial mode) were 
applied, ALL these pages would be WCD candidates. Right now, direct Apache/gunicorn with 
no CDN — no caching intermediary observed.

**Static assets**: 259 files, ALL with `Cache-Control: MISSING` but with `ETag` present.
Static files served without auth requirement (expected). ETags are stable Apache-format.

**WCD is currently a LOW-RISK surface** because there is no CDN/caching layer detected.
BUT: the complete absence of `Cache-Control: no-store` on HTML pages means if any proxy
is ever introduced, it becomes immediately exploitable across 20 endpoints simultaneously.

**Key WCP anomaly**: One `POST /api/reports/charts/` returned `Cache-Control: MISSING`
while all other API POST responses returned `no-cache, no-store, must-revalidate`.
This may indicate a different code path (streaming/SSE endpoint vs standard JSON).
Worth testing: does this endpoint reflect any request headers in its response?

### CSPT FINDINGS

**No classic CSPT found** — the application does NOT construct API request paths by 
concatenating URL parameters/hash values. The URL builder pattern is:
```
END_POINTS.urls()[endpointName] + "?action=" + encodeURIComponent(action) + "&CSRF_key=" + ...
```
All endpoint names are hardcoded string constants. No user input reaches the path segment.

**However — OPEN REDIRECT in Login-As flow**:
In `layout_subaccounts_dropdown.js`:
```js
var getRedirectUrl = function(data, fallbackUrl) {
  if (data && data.results && data.results.goto) {
    return data.results.goto;      // ← from server response
  }
  if (data && data.url) {
    return data.url;               // ← from server response
  }
  return fallbackUrl;
};
// ...
window.location = getRedirectUrl(data, fallbackUrl);
```
After `POST /api/login/` with `LOGIN_AS`, the client navigates to `data.results.goto`
or `data.url` from the server response. If the server can be made to return an attacker-
controlled `goto`/`url` value, this becomes an open redirect. Key question: can an attacker
influence what the server puts in `goto`?

**`/settings/subaccounts/undefined` — CSPT race condition bug**:
Request sequence: load subaccounts Vue → GET /api/settings/subaccounts/ → 
GET /api/settings/smtp_users/ → **GET /settings/subaccounts/undefined**

The subaccounts Vue app appears to build a navigation URL using a property that is
`undefined` at mount time (before the API response returns). The word "undefined" is a 
JavaScript uninitialized value serialized into a URL path. This isn't directly exploitable
but reveals that path construction uses dynamic values — making it a pointer to where
CSPT could exist if user-controlled data flows into the same variable.

**Paperform feedback URL with member_id**:
Found in `/settings/subaccounts/` HTML:
```html
<a href="https://smtp2go-feedback.paperform.co?m=1010395&p=/settings/subaccounts/">
```
The member_id `1010395` is embedded in a third-party feedback URL. Low impact but 
confirms master account ID leakage to Paperform (third-party analytics).

**Hash-based routing (sms-settings)**:
`window.location.hash.replace("#", "")` used to switch between tabs (general/dedicated/recharge).
`history.replaceState` cleans the hash from the URL. No API call uses the hash value — 
purely client-side tab switching. Not a CSPT vector.

**`window.location.replace(res.results.stream_url)` in reports-summary-table.tag**:
A PUT to `/api/reports/summary/` returns a `stream_url` which is navigated to via
`window.location.replace()`. If `stream_url` is user-influenced (e.g., via a crafted
export request), this could be an open redirect. Needs testing.

### ADDITIONAL FINDINGS

**Session Cookie Missing Secure + SameSite**:
`session=UUID; HttpOnly; Path=/` — No `Secure` flag means cookie could be sent over HTTP.
No `SameSite` means CSRF is possible in older browsers (though CSRF token exists).
The CSRF token being in the URL query param (`?CSRF_key=`) is also a problem — it appears
in Referer headers sent to third parties (Hotjar, Chargebee, etc.).

**CSRF Token Leakage to Third Parties**:
Every API call includes `?CSRF_key=<token>` in the URL. Pages load:
- Hotjar (`insights.hotjar.com`) — CORS allowed explicitly
- Chargebee (`chargebee.com/v2/chargebee.js`) — billing
- AnnounceKit — product announcements
- Zendesk Chat — support widget

The Referer header on resources loaded from these domains will contain the CSRF key.
