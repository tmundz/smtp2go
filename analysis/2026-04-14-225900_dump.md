## Critical New Findings

### JWT COOKIE ORIGIN IDENTIFIED
Row 186 response reveals: the cookie `1XJgM5twoV0e8IhkwW0BQuDwzkz` is set by smtp2go's OWN 
gunicorn server (not a third-party), on the `GET /dashboard/main/?login_id=<token>` 302 response.

This is the session-transition mechanism:
1. login_id cookie value → used as URL GET param: `GET /dashboard/main/?login_id=.eJw...`
2. Server validates the signed Flask token
3. Server responds: 302 to /dashboard/main/ + clears login_id cookie + sets JWT cookie
4. JWT cookie contains: external_id, user-agent, remote-addr, 12hr expiry
5. The JWT cookie persists across the session as a secondary identity token

Server mitigations: `Referrer-Policy: no-referrer` + `Cache-Control: no-store` on the 302 response.
This prevents the login_id URL from appearing in Referer headers and prevents caching.

**But**: the JWT cookie `1XJgM5twoV0e8IhkwW0BQuDwzkz` does NOT have:
- HttpOnly: true ← NOT set! (visible in the Set-Cookie: ...HttpOnly; Path=/ lines above)
  Wait, checking again: `set-cookie: 1XJgM5twoV0e8IhkwW0BQuDwzkz=...; Expires=...; Max-Age=2592000; HttpOnly; Path=/`
  Actually it DOES have HttpOnly! Correction: cookie IS HttpOnly.
- Secure flag: NOT present
- SameSite: NOT present

### CORS GLOBAL MISCONFIGURATION (CRITICAL)
`Access-Control-Allow-Origin: http://insights.hotjar.com` + `Access-Control-Allow-Credentials: true`
is present on ALL 362 responses from app-us.smtp2go.com.

This includes:
- All 20 authenticated HTML pages
- All API endpoints (confirmed on /api/dashboard/main/)
- All static assets (/static/*)
- The /end-points/ response
- The /zdesk_chat_auth response

**Attack surface**: If an attacker gains JavaScript execution on http://insights.hotjar.com
(via XSS, supply chain compromise, or DNS hijacking), they can:
1. Make credentialed XHR to any smtp2go API endpoint
2. Read the response (including CSRF tokens, API keys, email data, account IDs)
3. The browser will allow this because ACAO explicitly allows that origin + ACAC: true

The ACAO uses `http://` (not `https://`), which is:
- A weaker origin (unencrypted connection possible)
- A signal this might be a mistake (Hotjar is HTTPS but they used HTTP in the policy)

**Exploitation chain**:
1. XSS on insights.hotjar.com OR DNS hijack of insights.hotjar.com
2. Hotjar JS loaded on victim's smtp2go dashboard
3. Attacker JS on Hotjar domain makes: `fetch('https://app-us.smtp2go.com/api/settings/api_users/?action=load-active-users&CSRF_key=...', {credentials: 'include'})`
4. Browser allows response because ACAO allows Hotjar origin
5. Attacker reads: API keys, webhook URLs, SMTP credentials, email sending history
