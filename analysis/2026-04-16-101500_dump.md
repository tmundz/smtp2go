## Impact on SSRF Scenarios

### Scenario 3 (Critical, cloud metadata credentials): EFFECTIVELY DEAD

Linode metadata service differs from AWS in two critical ways:
1. **Requires token**: PUT /v1/token with Metadata-Token-Expiry-Seconds header first
   - The webhook SSRF surface makes a GET (or POST) request — cannot get the token first
   - No single-request auth bypass like AWS IMDSv1
2. **No credentials**: even if you bypass token auth, Linode metadata returns instance info
   (label, region, type, IPs) — NOT IAM/API credentials
   - There is no `/iam/security-credentials/` equivalent on Linode

Scenario 3 likelihood: **~4%** (down from 22%)
Only surviving path: if smtp2go stores Linode API tokens or DB credentials in
instance user-data (non-standard but possible). Very unlikely.

### Scenario 2 (High, internal network read): STILL ALIVE

This is now the ceiling for this SSRF. Internal services on the same Linode instance:
- Likely: PostgreSQL (5432), Redis (6379), internal Django/Gunicorn ports (8000/8080)
- Possible: Celery workers, internal APIs, admin panels
- Linode instances typically run all services on localhost, not exposed externally
